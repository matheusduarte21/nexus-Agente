# ADR-011 — Adoção de PostgreSQL, pgvector e Drizzle ORM

**Status:** Aceito

## Contexto

A Nexus Commerce requer armazenamento persistente para sessões de conversa, conhecimento corporativo, *embeddings*, solicitações de cancelamento e registros de auditoria de negócios.

O desafio técnico exige recuperação semântica de documentos mantendo segurança, reprodutibilidade e baixa complexidade operacional.

## Decisão

Adotaremos o **PostgreSQL 17** com a extensão **pgvector** como infraestrutura de armazenamento relacional e vetorial.

* O **Drizzle ORM** fornecerá acesso tipado ao banco de dados por meio do driver `node-postgres`.
* O **Drizzle Kit** gerenciará as migrações SQL controladas por versão.
* O **Docker Compose** fornecerá um ambiente de banco de dados local reprodutível.

### Controles de segurança
* Papéis (*roles*) separados no banco de dados para administração, migração e aplicação.
* Credenciais da aplicação sem privilégios de superusuário (*superuser*).
* Permissões explícitas em nível de tabela.
* Nenhuma modificação automática de *schema* durante a inicialização da aplicação.
* Porta do banco de dados restrita a `localhost` durante o desenvolvimento local.
* Credenciais separadas para tempo de execução (*runtime*) e migração.
* Configuração de conexão validada.
* Limites de *pool* de conexões e *timeouts* de consultas (*queries*).
* Mensagens de erro relacionadas ao banco de dados sanitizadas.
* Respostas públicas mínimas de prontidão (*readiness*).

## Alternativas consideradas

* PostgreSQL combinado com Qdrant.
* PostgreSQL combinado com um banco de dados vetorial gerenciado.
* Sequelize.
* TypeORM.
* SQL direto sem um ORM.

## Justificativa

O PostgreSQL e o pgvector oferecem persistência relacional e busca por similaridade vetorial dentro da mesma infraestrutura.

O Drizzle fornece acesso tipado ao banco de dados orientado a SQL e gerenciamento explícito de migrações.

Uma única instância de banco de dados reduz a complexidade operacional para o desafio técnico atual.

O volume inicial de documentos não justifica um banco de dados vetorial dedicado ou índices de vizinhos mais próximos aproximados (*Approximate Nearest Neighbor* — ANN).

## Restrições arquiteturais

* Os casos de uso (*use cases*) de negócios devem depender de portas (*ports*) de repositório, e não do Drizzle ORM ou de implementações específicas de banco de dados.
* O acesso ao banco de dados será realizado por adaptadores de infraestrutura.
* A aplicação não utilizará credenciais administrativas ou de migração.

## Consequências

* As migrações de banco de dados devem ser revisadas e versionadas.
* Os papéis (*roles*) do banco de dados e as permissões de tabela devem ser mantidos conforme o *schema* evolui.
* A configuração inicial do *pool* de conexões deve ser calibrada antes da implantação em produção.
* Variáveis de ambiente locais e volumes Docker não substituem o gerenciamento de segredos em produção, o armazenamento criptografado ou as políticas de backup.

## Verificação

A aplicação deve verificar a configuração do banco de dados, a execução das migrações, o comportamento de prontidão (*readiness*), a disponibilidade da extensão vetorial e o acesso com privilégio mínimo (*least-privilege*).

Testes automatizados de integração com o banco de dados serão adicionados durante a etapa de segurança de persistência.
